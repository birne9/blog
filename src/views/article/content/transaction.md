## 什么是事务

一笔业务经常要连续执行多条 SQL,而且要求它们要么全部成功,要么全部失败。比如新生入学,要登记两件事:在学生表插入一条学生记录,再在关联表登记他的任课老师。两步必须同时生效,不能出现"学生插进去了、老师关系没登记上"的半成品。把多条语句打包成一个整体执行,就是事务(Transaction)。

事务有四个特性,简称 ACID:原子性(Atomicity),语句打包,要么全成要么全败;一致性(Consistency),事务前后数据都满足业务规则,比如学生表和关联表永远对得上;隔离性(Isolation),多个事务并发执行互不干扰;持久性(Durability),提交后的数据不会因为断电丢失。

事务的三条基本命令:START TRANSACTION 开启事务,BEGIN 是它的简写;COMMIT 提交,让修改永久生效;ROLLBACK 回滚,撤销事务内的所有修改。下面把入学登记的两步打包成一个事务,LAST_INSERT_ID() 取上一条 INSERT 刚生成的自增 id:

```sql
START TRANSACTION;
INSERT INTO students (class_id, name, gender, score) VALUES (2, '新生', 'M', 88);
INSERT INTO student_teacher (student_id, teacher_id) VALUES (LAST_INSERT_ID(), 1);
COMMIT;
```

第二句如果执行失败(比如老师 id 不存在),程序会调用 ROLLBACK,第一句插入的学生记录也会被撤销,数据库恢复原状。这就是原子性的价值:中间任何一步出错,整个事务像没发生过一样。

> 前端类比:事务就像一次批量 DOM 操作,希望要么全部生效要么全部还原,而不是改了一半崩了留下残局。JS 单线程天然不会出现"另一段代码中途插进来改同一块数据",但数据库同时服务很多连接,两个事务可能同时操作同一张表,所以必须靠事务机制保证安全。

## 四种隔离级别

多个事务并发跑时,会互相干扰,产生三类典型问题:脏读(读到了别的事务还没提交的修改)、不可重复读(同一事务里两次读同一行,值不一样,因为中间别人提交了修改)、幻读(同一事务里两次查询,行数不一样,因为中间别人插入了新行)。

隔离级别就是"允许多大程度的互相干扰",SQL 标准定义了四级,从松到严:

Read Uncommitted(读未提交):允许脏读,别人没提交的修改都能读到,几乎没人用,因为读到的东西随时可能被回滚掉。

Read Committed(读已提交):不允许脏读,只能读到别人已提交的数据,但允许不可重复读。大多数数据库(Oracle、SQL Server)的默认级别。

Repeatable Read(可重复读):同一事务里多次读同一行,结果保持一致,不允许脏读和不可重复读,但仍可能幻读。这是 MySQL 的默认级别。

Serializable(串行化):最严格,事务完全排队执行,任何问题都不会出现,但并发性能最差。

修改当前连接的隔离级别用 SET 语句:

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

## 脏读与不可重复读

看两个具体场景,就能理解隔离级别的差异。假设小明的成绩初始是 90。

场景一:事务 A 把小明的成绩改成 60 但还没提交;事务 B 读到 60,以为小明不及格。随后 A 回滚了,成绩还是 90,B 读到的 60 是"脏数据"。Read Committed 及以上级别不会出现:没提交的数据,别人读不到。

场景二:事务 A 第一次读小明的成绩是 90;此时事务 B 把成绩改成 100 并提交了;A 第二次读,变成 100。A 明明是同一个事务,两次读到不同值,好像数据"反复无常"。Repeatable Read 及以上级别不会出现:事务开始后,读到的行就像拍了快照,别人后来的修改不影响它。

幻读比不可重复读更隐蔽:事务 A 查"成绩大于 80 的学生"得到 5 行,此时事务 B 插入了一个成绩 95 的新学生并提交,A 再查一次,得到 6 行,多出来的一行就像幻觉。只有 Serializable 能完全杜绝。

> 前端类比:脏读相当于你打开了别人正在编辑、随时可能撤销的草稿,还把它当成正式内容。不可重复读相当于你拿着一个月前的缓存快照和最新的接口数据对比,两次对不上。隔离级别本质是"拿快照还是拿实时数据"的权衡:Read Committed 每次读都拿最新已提交值,Repeatable Read 事务开始时拍一张快照全程复用,Serializable 干脆所有人排队,不允许并发。

## 为什么 MySQL 默认可重复读

MySQL 默认 Repeatable Read,比 Read Committed 更"安全"一点,而且 MySQL 通过 MVCC(多版本并发控制)实现了不锁表的可重复读,性能损失可接受,并且实际效果上连幻读也基本防住了。

日常开发的选择很简单:没有特殊要求就用默认的 Repeatable Read,把心思花在业务正确性上。另外记住一条经验:事务里不要放耗时操作(比如远程调用),事务越短越好,长时间不提交的事务会锁住数据,拖垮整个库。

> 前端类比:长事务就像 JS 里 hold 住一个大锁不放,别人都得等着。事务里做远程 HTTP 调用,相当于把网络请求的不可控耗时也包进了临界区,数据库连接被占着,并发量直接雪崩。

## 小结

事务是写操作的保险丝:多条语句打包,COMMIT 生效,ROLLBACK 撤销。隔离级别在"安全"和"并发性能"之间取平衡,记住四个级别从松到严,以及它们各自挡住的问题:Read Uncommitted 什么都不挡,Read Committed 挡脏读,Repeatable Read 再挡不可重复读,Serializable 全挡但最慢。到这里 SQL 主干知识就完整了:表结构与索引、查询、增删改、事务,接下来可以拿一个小项目(比如学生成绩管理系统)把这些串起来练一遍。
